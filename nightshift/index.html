Two-person lab · est. October 2026

Security isn't about breaking in. It's about knowing what holds.

Six missions, one at a time. You're on the keyboard. I untangle it when it knots. Nobody here watches videos and calls that learning.

Every mission is a short program that tells you something true and uncomfortable about systems you already use daily. Six missions in, you won't have a certificate — you'll have a public folder of working code with your name on it, which is the thing people in this field actually get hired on.

Assumed knowledge: none. Not Python, not the command line, not GitHub. If you've never written a line of code, you're exactly who this is built for — Start here explains the vocabulary, and Resources says where to learn each piece properly.

How you got in

You're reading this, so the gate didn't hold. Find the paragraph that matches how you did it — the route you took decides which lesson you just learned.

you read the page without the word

Then it was never protected. A gate written in JavaScript sends your browser the entire page first and hides part of it afterwards. The decision about what you're allowed to see was made on your computer — the one machine in this story that you fully control. View source, developer tools, disabling JavaScript, or a single curl all walk straight past it.

you tried to crack the hash first

Good instinct, and it got you nowhere — which is the interesting part. The code holds a SHA-256 rather than the word itself, and this particular passphrase has never appeared in a single breach, so no lookup table on earth contains it. Precomputation, the trick from exercise 3, simply has nothing to work with here. By the standard of exercise 4 it is a genuinely strong secret.

And you still got in, in well under a minute. That's the whole lesson: the password was never the weak part. A strong secret guarding a broken design is still a broken design.

what would have actually worked

A check that happens on a server you don't control, before the page is ever sent. The server simply never hands over what you aren't allowed to see, so there's nothing on your machine to inspect, edit or skip. "Never trust the client" is the whole idea, and it's one of the few rules in this field with almost no exceptions.

the part the gate can't fix

Even with a perfect login, this page would still be sitting in a public repository on GitHub, readable by anyone, with no gate anywhere near it. The address was unlisted, which is not the same thing as protected. That gap has a name — security through obscurity — and it's one of the oldest and most expensive mistakes there is.

Start here

Four words show up constantly below. If any of them are fuzzy right now, that's the normal starting position — nobody is born knowing them. Here they are in plain language, and Resources says where to go deeper on each.

the terminal

A text-only way to tell your computer what to do. Instead of double-clicking an icon, you type the name of what you want and press Enter. On Windows it's called PowerShell or Terminal — press Win+X and it's in the menu. It looks hostile and it's really just a conversation: you type a line, it answers. Everything in this lab happens here.

python

A programming language — a vocabulary and set of rules for writing instructions a computer will follow. It was designed to be readable by humans, which is why most security tooling you'll meet is written in it. You install it once, and from then on your machine understands files ending in .py.

a script

A plain text file full of those instructions, run from top to bottom. That's the whole idea. pwned.py is a script — you can open it in Notepad and read every line. Nothing is compiled, hidden or sealed. If you can read it, you can change it, and changing it is how this lab works.

git and github

Git is a tool on your computer that records every change you make to your code, like an infinite undo history with notes. GitHub is the website that stores those histories online. People use the two words interchangeably, which is confusing — that's the actual difference. It matters because GitHub is the closest thing this field has to a résumé.

Mission 01 — Pwned?

Get the tool running first — that part takes about ten minutes. Everything after it is thinking, not typing. The program is the instrument; the six exercises are the actual mission, and five of the six are answered in words.

Get the tool

One file. No installer, no libraries to add, nothing to sign up for. Seventy-one lines you can read start to finish in about two minutes.

Download pwned.py

71 lines · 2.5 KB · Python 3.8 or newer

  1. Install Python

    Get it from python.org/downloads and run the installer.

    On the very first screen, tick the box that says "Add python.exe to PATH" before you click Install. It sits at the bottom and it's easy to miss. That single checkbox is the difference between step 5 working and step 5 throwing an error.

  2. Check that it worked

    Press Win + X and pick Terminal. Type this and press Enter:

    python --version

    You want a version number back, like Python 3.12.4. Anything else, see Snags below.

  3. Download it, then read it

    Use the button above. It lands in your Downloads folder.

    Now open it in Notepad and actually read it first. Rule zero of this field: you don't run code you haven't looked at. It's seventy-one lines and most of them are comments explaining the next four steps of what it does. Start the habit on a file you already trust.

  4. Point the terminal at that folder

    Back in the Terminal window:

    cd ~\Downloads

    The prompt changes to show you're now in that folder. The terminal only ever acts on where it currently is — that's most of what "navigating" means here.

  5. Run it

    python pwned.py

    It asks for a password. Nothing will appear as you type — no dots, no stars, nothing. That's deliberate, not a frozen keyboard. Type it and press Enter.

    Start with a password you'd have called strong five minutes ago.

Snags

'python' is not recognized as an internal or external command
The PATH box in step 1 wasn't ticked. Run the installer again, choose Modify, and make sure "Add python.exe to PATH" is on. Then close the Terminal and open a new one — it only reads PATH when it starts.
The Microsoft Store opens instead of Python
Windows ships a placeholder that hijacks the word python. Go to Settings → Apps → Advanced app settings → App execution aliases, and switch off both python.exe and python3.exe.
can't open file 'pwned.py': No such file or directory
The terminal isn't in the folder holding the file. Redo step 4. If you saved it somewhere other than Downloads, cd to that folder instead.
URLError or a connection error
The lookup needs the internet — it's asking a public breach database for a batch of hashes. Your password still isn't going anywhere; see the code if you want to confirm that yourself.
  • Exercise 1 · 5 minutes

    Run the tool and give it password. It prints a line starting SHA-1 hash : — write those 40 characters down. Run it again with Password. One letter, now capitalised. Write the new hash underneath the old one.

    Compare them character by character. How much of it stayed the same?

    This is the avalanche effect, and it's deliberate. A good hash has no concept of "nearly right" — one flipped bit on the way in scrambles roughly half the bits coming out. That's what kills guessing-by-approach: there's no warmer-or-colder to follow, so every wrong guess tells you exactly nothing.

  • Exercise 2 · 5 minutes

    Take one of those 40-character hashes. Your job is to get the password back out of it. You won't manage it — spend three minutes on why not, then write the reason in your own words.

    Here's the clue that cracks it open: that hash is exactly 40 characters whether you fed it a 3-letter password or the complete text of a novel. So where did the rest of the novel go?

    It was thrown away. A hash isn't encryption — encryption keeps everything, locked, so the right key opens it again. A hash destroys. You can blend a fruit into a smoothie and you cannot un-blend it, no matter how good your blender. That property has a name: one-way, or preimage resistance.

  • Exercise 3 · 10 minutes

    Hold exercises 1 and 2 side by side and you have a contradiction to solve. Nobody can reverse a hash. Yet the database this tool talks to knows, with certainty, that a particular hash means password123 and that 2,266,543 people used it.

    How? Write your answer before reading the next paragraph.

    Nobody reversed anything. The same input always produces the same output — that's the whole point of a hash — so an attacker hashes every candidate password forwards, once, and keeps the results in a giant lookup table. Then cracking a stolen database is just looking things up. The property that makes hashing useful is the same property that makes it attackable. The fix is called a salt: a random value mixed into each user's password before hashing, so two people who both picked password123 get two different hashes and the attacker's prebuilt table is worth nothing.

  • Exercise 4 · 15 minutes · the big one

    Run the tool on these three and write down what comes back: P@ssw0rd, then mycathatesmondays, then something you invent on the spot.

    P@ssw0rd has a capital, a symbol, a digit and a substitution. It looks like it was built to a password policy. It's been breached over six million times. The seventeen lowercase letters have never been seen. Why?

    Entropy is not how strange a password looks to a human. It's the size of the pile an attacker has to search through, given what they already know about how people choose. Nobody attacking P@ssw0rd treats it as eight unknown characters — they treat it as one common word with the four obvious substitutions, which is a list of a few million. Being "complex" to look at bought nothing, because the attacker never guessed character by character in the first place.

  • Exercise 5 · 15 minutes

    Read the table below. Each row is a way of choosing a password; the last two columns are how long one high-end graphics card would need to grind through every possibility, depending on how the website stored it.

    Two things to answer: which row surprised you, and which of those two columns can you personally do anything about?

    You pick the row. The website picks the column. SHA-1 is fast on purpose — that's a virtue when you're checking a downloaded file hasn't been tampered with, and a disaster when you're storing passwords, because fast means cheap to guess. bcrypt and argon2 are built to be deliberately, tunably slow. Same password, same attacker: hours or millennia, decided entirely by someone you've never met. That asymmetry is why unique passwords per site matter more than clever ones.

  • Exercise 6 · no right answer

    The tool sends the first five characters of your hash to a stranger's server and swears your password never leaves the room. Interrogate that claim.

    Could the server work out your password from those five characters? What if it quietly logged every lookup you made for a year — does the picture change? What if you were the only person on earth using this tool?

    There is no clean answer, and that's the point. Everything in security is a trade made against a specific opponent with specific resources. Being able to argue this one carefully — "safe against whom, doing what, for how long" — is closer to the actual job than any tool you'll ever learn.

Finishing: your first commit

Mission 01 ends with your answers on GitHub. You've never done this before, so here is all of it — what the words mean, the exact commands, and every error you're likely to hit. Budget half an hour the first time and about forty seconds every time after.

repository

A folder that git is watching, plus the complete history of everything that has ever been in it. When you run git init, a hidden .git folder appears inside — that folder is the repository. Delete it and you have an ordinary folder again with no history.

commit

A snapshot of your files at one moment, sealed and labelled with a message you write. A commit does not upload anything. That is the single most common misunderstanding about git, and it trips up nearly everyone: committing is local, sending is a separate act.

staging

The step between editing and committing, where you choose which changes belong in the next snapshot. git add puts things in the box; git commit seals and labels it. It feels like a pointless extra step until the first time you want to save half of what you changed.

push

Sending your sealed commits to GitHub. Until you push, everything you've done lives only on your laptop — which also means a laptop failure takes it all with it. origin is just git's default nickname for "the copy on GitHub".

Where a file actually is, at each stage

  1 YOUR FOLDER          2 STAGING           3 COMMIT            4 GITHUB
  what Explorer shows    what you picked     sealed + labelled   the online copy
                         for the next box    kept in .git        other people see

  answers.md   --git add-->   answers.md   --git commit-->   snapshot   --git push-->   snapshot
  pwned.py                   pwned.py                            + message                   + message

  |---------------- all of this is still on your laptop ----------------|  |-- now public --|

  1. Install Git

    Download it from git-scm.com/download/win. The installer asks a lot of questions — accept every default. One of those defaults installs Git Credential Manager, which is what handles your GitHub login later without you ever creating a token by hand.

    Close your Terminal, open a fresh one, and check:

    git --version

  2. Tell Git who you are — once, ever

    Every commit is signed with a name and an email. Git refuses to make one until it knows yours.

    git config --global user.name "Your Name" git config --global user.email "you@example.com"

    Use the same email address as your GitHub account, or your commits won't be linked to your profile and the work won't show up as yours. --global means "every project on this machine", so you do this one time and never again.

  3. Put the work in one folder

    Make a folder called cyber-lab and put two files in it: pwned.py, and answers.md with your written answers to the six exercises. That folder is what's about to become public, so look at what's in it before you continue.

  4. Create the empty repository on GitHub

    On github.com/new: name it cyber-lab, leave it Public, and do not tick "Add a README file". An empty repository makes the first push far simpler — ticking that box is the cause of the most confusing error in the Snags list below.

    Click Create, then copy the URL it shows you. It looks like https://github.com/your-username/cyber-lab.git.

  5. Turn your folder into a repository

    Point the Terminal at the folder, then initialise it:

    cd ~\Downloads\cyber-lab git init -b main

    A hidden .git folder appears. The history will live in there from now on. -b main names your first branch main, which is what GitHub expects — without it older versions of git pick master and the names won't match.

  6. Choose what goes in, then seal it

    git add . git commit -m "Mission 01: answers on hashing and entropy"

    The . means "everything in this folder". The -m is the message, and it's for a human reading it in six months — write what changed and why, never "update".

    You now have a commit. Nothing has been uploaded yet. It exists only inside that .git folder on your laptop.

  7. Connect it to GitHub and send it

    git remote add origin https://github.com/your-username/cyber-lab.git git push -u origin main

    The first line teaches your folder where its online twin lives; origin is just a nickname for that URL so you don't retype it. The second line sends everything.

    A browser window will open asking you to sign in to GitHub. That's Git Credential Manager doing its job — it stores the login, so this is the only time you'll see it. Refresh your GitHub page and your files are there.

  8. From now on, the loop is three lines

    git add . git commit -m "what I changed" git push

    That's it. Steps 1 through 5 were setup you never repeat for this project.

The one habit worth building

  • Run git status after every single command above. It tells you which files git has noticed, what's staged, and what's been committed but not pushed — in plain English, with suggestions. Beginners who run it constantly understand git in a week. Beginners who don't stay confused for a month. It changes nothing and cannot break anything, so there is no reason not to.

Git never forgets — and that's a security problem

  • If you commit a password, an API key, or a private file and then delete it in a later commit, it is still in the history. Anyone who clones the repository can read it. Deleting a file does not delete its past; that's the entire point of version control.
  • This is a real and common cause of breaches, not a hypothetical. Bots watch the stream of new public commits and scrape credentials out of them within minutes of being pushed. People who notice their mistake and delete the file an hour later still get compromised.
  • So the rule is simple and it goes before git add ., not after: know what is in the folder. If a secret ever does get pushed, deleting it is not the fix — you treat that credential as burned and replace it.

Snags

'git' is not recognized as an internal or external command
Either Git isn't installed, or your Terminal was already open when you installed it. Close every Terminal window and open a new one — it only reads the list of available programs when it starts.
Author identity unknown / Please tell me who you are
You skipped step 2. Run those two git config lines and then run your git commit again.
Authentication failed, after you typed your GitHub password
GitHub stopped accepting account passwords for git in 2021. Let the browser window handle the login instead. If no window appears, go to GitHub → Settings → Developer settings → Personal access tokens, generate one with repo access, and paste that in place of the password.
src refspec main does not match any
You're pushing something that doesn't exist yet. Either nothing has been committed (redo step 6), or your branch is called master rather than main. Fix the name with git branch -M main and push again.
Updates were rejected because the remote contains work that you do not have locally
You ticked "Add a README file" when creating the repository, so GitHub has a commit your laptop has never seen. Run git pull --rebase origin main, then push again.
remote origin already exists
The first line of step 7 ran twice. Replace the address instead of adding it: git remote set-url origin <your url>.
It pushed, but GitHub says the commits aren't mine
The email in step 2 doesn't match one on your GitHub account. Fix it with the same git config command, or add that address under GitHub → Settings → Emails. Commits already made keep the old address.

Concepts

Added as they come up. If a word here doesn't mean anything to you yet, that's the next conversation.

hash

A one-way blender. Any input — a word or a whole book — comes out as a fixed-length code. Information is destroyed on the way through, which is why nobody reverses it. Change one character of the input and roughly half the output bits flip: the avalanche effect, which is what makes guessing-by-getting-warmer impossible.

entropy

The size of the pile an attacker must search, given what they know about how you chose. Not how odd the password looks. P@ssw0rd is not eight unknown characters; it's one dictionary word with predictable substitutions, so the real pile is a few million and it falls instantly.

salt

A random value mixed into each password before hashing, stored alongside it. Two people who both chose password123 then end up with completely different hashes. It doesn't make your password better — it makes the attacker's prebuilt lookup table useless, forcing them to attack every account separately.

key stretching

Choosing a hash that is deliberately slow. SHA-1 is fast, which is a virtue for checking a downloaded file and a catastrophe for storing passwords. bcrypt and argon2 are tunably slow, turning hours of attacker time into millennia. The site picks this, not you — which is the argument for a different password everywhere.

k-anonymity

Hiding a question inside a crowd of questions. The tool asks for all ~1,900 records sharing the first five characters of your hash, so the server learns that you asked something but never what. Privacy built into the shape of the request rather than promised in a policy you can't verify.

threat model

Naming who you're defending against before defending anything. "Secure" isn't a property a system has; it's a sentence that needs finishing — secure against whom, doing what, for how long. Exercise 6 is a threat model with the training wheels on.

security through obscurity

Relying on something being hard to find rather than hard to open. An unlisted URL, a renamed admin page, a hidden folder. It isn't worthless as an extra layer, but it collapses completely the moment someone looks, and it tends to be mistaken for the real thing. If your defence stops working once the design is known, it was never a defence.

trust boundary

The line where data stops being under your control and starts being under someone else's. Everything the user's browser holds — the page, the JavaScript, the hidden fields, the disabled button — is on their side of that line and can be rewritten at will. Checks worth anything happen on your side. The gate on this page put the line in exactly the wrong place.

When you're stuck

  • The error message your first move, every time

    Copy the last line of the error and paste it into a search engine, word for word. Someone has hit the exact same wall and written about it. Reading errors is a skill, and it's most of the job.

  • Ask me after ten minutes, not before

    House rule 2. The ten minutes aren't a punishment — they're where the learning actually happens. After that, asking is the right move, not a failure.

House rules

  1. You're on the keyboard. Watching someone else type is entertainment, not training. If your hands aren't moving, nothing is going in.
  2. Fight it for ten minutes before you ask. Then ask. Short frustration teaches; long frustration makes people quit. Ten minutes is the line.
  3. Breaking it is data. A stack trace is the program telling you exactly where it stopped understanding you. Read it top to bottom. It isn't an insult.
  4. Every mission ends with a commit. Working code that only exists on your laptop may as well not exist. Saving it to GitHub is called a commit. If that sentence means nothing yet, First commit walks through every step of doing one for the first time.
  5. Only ever attack what is yours. Your machine, your network, your accounts, or a lab that was deliberately built to be attacked. Not the neighbour's Wi-Fi, not your school, not a company whose website looks sloppy, not "just to see whether it works". Scanning a network you don't own is not a grey area, and it doesn't become one because nothing broke and nobody noticed. In the US the line has a name — the Computer Fraud and Abuse Act — and it's federal. Every single thing in this lab is legal purely because of where it points. Change the target and you've changed what it is, instantly and entirely.
  6. Every genuinely good hacker I've met has stayed out of prison. That isn't luck, and it isn't because the temptation never came up. The skill that keeps you free isn't a technical one — it's the judgment you apply in the two seconds before you open a door, every time, for the rest of your career. And never underestimate the people whose job is catching you: they are patient, well funded, and they do this full time. There is always someone smarter than you. They only have to be right once; you have to be careful every single time. The ones who last make that trade consciously, and they make it early.
